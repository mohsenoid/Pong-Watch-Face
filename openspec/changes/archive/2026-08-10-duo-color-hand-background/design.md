## Context

Current background is a single opaque `bg_scanlines.png` `PartImage` drawn first in the `Scene`, beneath the `DigitalClock` digits and the `arcade_track` arena `Group`. Digits are a mix of `TimeText` (the three live positions: `hh_1`, `mm_10`, `mm_1`) and `PartImage` (the conditional hour-tens digit and the colon) — a split that already exists because of an earlier discovery that a single combined `TimeText format="hh:mm"` drops its first character on this runtime.

This project has repeatedly found that WFF's actual supported behavior is narrower than its documentation suggests. During this change's own implementation, `<Transform target="rotationDegrees">` was confirmed **not** to apply to a generic `PartImage` at all — tested with both a `[MINUTE]`-based expression and a hardcoded literal value, neither rotated the image (verified via precise pixel measurement of the dividing line's position across multiple screenshots). Rotation only works through `AnalogClock`'s dedicated `HourHand`/`MinuteHand`/`SecondHand` elements via their `pivotX`/`pivotY` attributes (confirmed in the official `SimpleAnalog` sample).

**Mid-implementation, the user changed direction**: instead of a rotating diagonal two-color split (a real Wear OS "hand-driven" duo watch face they liked), they found a different reference — a "Split" style face with a **static** horizontal-ish divide (muted dark top, bright orange bottom) — and asked to use that instead, still with color-swapping digits, plus day-of-week and date text added at the top. A static split sidesteps the rotation problem entirely (no `Transform`/`AnalogClock` rotation needed at all), so this revision is strictly simpler on the riskiest axis, while keeping the masking risk from the original plan.

See proposal.md for the (now superseded) original why; the core "digits swap color across a two-tone split" idea carries over, just with a static rather than rotating divide, a different color palette (dark charcoal / orange, not purple / orange), and an added date/day-of-week requirement.

## Goals / Non-Goals

**Goals:**
- A static two-color background split roughly horizontally (dark charcoal above, orange below), matching the new reference's general proportions rather than a rotating diagonal.
- Digits that visibly change color depending which background half they're over, reusing only the two background palette colors (no third color) — same masking-based approach as originally planned, just against a fixed rather than rotating split.
- Day-of-week and date text added near the top of the face, in the dark region.
- Keep the Pong arena exactly as it is visually (per explicit user choice) — verify contrast holds, don't redesign it.
- Verify the one remaining risky WFF mechanism (mask clipping, and specifically whether it composes with `TimeText`) cheaply before committing to the full digit-duplication build-out.

**Non-Goals:**
- No rotation of any kind — the earlier rotating-hand concept is dropped entirely per the user's direction change, not merely deferred.
- No true per-pixel color inversion (e.g. a `DIFFERENCE`/`EXCLUSION` blend mode) — masking remains the plan for the same reason as before: it reproduces "digit shows the *other palette color*" exactly, where a blend mode would compute an arbitrary negative instead, and this project has learned not to trust documented-but-unverified WFF behavior.
- No redesign of the Pong arena's colors/positions.
- No changes to the digit *shapes* (still the transcribed Atari font), hour-tens logic, ambient time text, or branding.

## Decisions

**Bake the split (and any tilt) into a single static PNG generated by PIL, not into WFF at all.** Since the divide no longer moves, there is no need for any WFF-level positioning/rotation trick — `generate_pixel_assets.py` composes one 450x450 image with the top region dark charcoal `(40,40,45)` and the bottom region orange (reusing the existing accent `(255,106,0)`), split by a horizontal line at `y=205` (chosen so the digit row, which spans `y=148` to `y=252`, straddles it with roughly its upper half over dark and lower half over orange — echoing the reference's numerals crossing the divide). This sidesteps the rotation limitation discovered above entirely: it's just a background image like `bg_scanlines.png` always was.

**Digit color-swap via `renderMode="MASK"`, with a two-tier fallback if it doesn't work as documented.** Unchanged in mechanism from the original plan, just against the static split instead of a rotating one: for each digit position, render two copies — one dark, one orange — each paired with a `renderMode="MASK"` copy of the *opposite*-colored half of the same static split image (no `Transform` needed on the mask either, since it's static), so only the portion of each digit copy over the matching background half is visible. Fallback tier 1 (if masking doesn't apply to `TimeText` specifically, matching the earlier `Transform` finding): convert the three live `TimeText` digits to the `PartImage`-with-per-value-`Condition` pattern already used for the hour-tens digit (10 conditional images per position instead of 1 `TimeText`) and retry masking on those. Fallback tier 2 (if masking doesn't work at all on this runtime): drop the color-swap effect, keep digits a single fixed color with good contrast against both backgrounds (e.g. white) — still delivers the two-tone split look, just without the per-digit color-swap detail.

**Day-of-week and date text via `PartText`/`Template`, using `[DAY_OF_WEEK_S]`, `[MONTH_S]`, and `[DAY]` expression tokens.** These three tokens turned up in Android's own WFF documentation/samples search results (a day-name string, a month-name string, and a 1-31 day-of-month integer) but weren't confirmed in this project's own on-device testing yet — verify via `adb logcat` and a screenshot early, same discipline as everything else, before treating the exact token names/casing as settled. Positioned in the dark top region, above the digit row.

**Keep the existing accent orange; replace purple with dark charcoal.** Reusing `(255,106,0)` keeps continuity with the watch face's existing branding (already used for the Pong arena's absence of orange... no — already the established accent color throughout this project). Charcoal `(40,40,45)` replaces the indigo/purple from the original rotating-hand plan, matching the new reference's muted-dark-plus-vibrant-orange look instead of a two-saturated-color look.

**Scanline texture becomes a low-opacity overlay, not an opaque fill.** Unchanged from the original plan: same generation approach (faint horizontal bands) but rendered with real alpha (e.g. ~15-25%) instead of the current opaque fill, drawn after the new split background and before the digits/arena/date text.

**Pong arena colors and positions untouched.** Per explicit user choice. White paddles/divider and a yellow ball both have reasonable luminance contrast against dark charcoal and orange alike — verify visually rather than assuming it.

## Risks / Trade-offs

- [Risk] `renderMode="MASK"` may not behave as documented on this runtime, or may not compose with `TimeText` (this project's established pattern of surprises). → Mitigation: the two-tier fallback above; test masking on a `PartImage` pair first (cheapest, most likely to work given `PartImage` has been reliable throughout this project) before attempting it on `TimeText`.
- [Risk] The `[DAY_OF_WEEK_S]`/`[MONTH_S]`/`[DAY]` expression tokens are sourced from web search over Android's docs, not this project's own prior verification — exact names or casing could be wrong. → Mitigation: build and check `adb logcat` for parse/evaluation failures immediately, same as every other new expression this project has used; adjust token names based on what the log actually says if they don't work.
- [Risk] Doubling every digit position (2 color copies x masks) roughly doubles the digit-related XML and adds real complexity. → Mitigation: scope this change to just the four live digit positions + colon (5 elements x 2 copies = 10), no further.
- [Risk] Adding date/day text in the already-tight top region could collide with the digit row or the circular clip boundary (this project has hit exactly this kind of layout-vs-circle mistake before, twice). → Mitigation: compute/verify the visible x-range at the chosen y-position against the circle equation before placing it, then confirm with an on-device screenshot, not just the math.

## Migration Plan

Pure visual/resource change — no data, no persisted state, no build/manifest changes. Rollout: verify the masking mechanism in isolation first, then verify the date/day expression tokens in isolation, before building the full digit-duplication work on top of both; then verify the complete scene (split background, digit color-swap, date/day text, arena contrast, ambient mode still hides the arena and shows plain time text) on the Wear OS emulator. Rollback is a plain revert of the `watchface.xml` background/digit/date sections and the new drawable/script changes.
