- [x] 1.1 Write a local Pillow (Python) script that generates pixel-art digit glyphs 0-9 and a colon into individual PNGs in `watchface/src/main/res/drawable/` (e.g. `digit_0.png` ... `digit_9.png`, `digit_colon.png`) in the chosen Atari orange/red accent color, transparent background. Went through two revisions: first a procedural seven-segment renderer (after a hand-typed dot-matrix attempt rendered illegibly), then replaced with a direct 6x8 pixel-grid renderer once the user shared an Atari 2600-style font byte-table reference and asked to reproduce it exactly. Flagged the copyright nuance (this is Atari's own BIOS typeface, not just a genre-inspired style) before proceeding; the user made the call to use it as-is for this personal/unpublished project. Transcribed via small cropped images (the full 80-row table was too error-prone to read reliably) and bit-verified against the source (each byte's bits 6..1 = one 6px-wide row).

## 2. Active-mode scene in watchface.xml

- [x] 2.1 Add a `BitmapFonts`/`BitmapFont` block registering the digit and colon glyphs from task 1.1, with correct `width`/`height` per character.
- [x] 2.2 Replace the placeholder background/greeting content with a `PartImage` referencing `bg_scanlines` as the base layer.
- [x] 2.3 Replace the existing `DigitalClock`/`TimeText` active-mode font with the new `BitmapFont` family, sized and centered for the 450x450 canvas. On-device testing found a single `TimeText format="hh:mm"` never renders its first character on this emulator's system image (the official `SimpleDigital` sample from `android/wear-os-samples` uses exactly that pattern successfully, so this looks like an image-specific quirk, not a general WFF limitation). Worked around by using one `TimeText` per digit (`hh_1`, `mm_10`, `mm_1` — single-digit format tokens) plus a separate `PartImage` for the hour-tens digit, shown only when the hour's tens digit is "1" (12-hour time only ever has a blank or "1" there). That digit needed its own dedicated drawable (`hour_leading_one.png`, duplicate of `digit_1.png`) — a drawable referenced by both a `BitmapFont` Character map and a plain `PartImage` fails to render in the `PartImage` on this runtime.
- [x] 2.4 Add a `Group` containing `PartImage` for `river_strip` and `PartImage` for `sprite_jet`. Two real bugs found and fixed via `adb logcat --pid=$(adb shell pidof -s com.google.wear.watchface.runtime)` (the WFF runtime logs expression parse failures - this was the key unlock, per the samples repo's README debugging tips):
  - Setting `x`/`alpha` directly as an attribute string containing an expression does not evaluate dynamically - it's either ignored (silently frozen at whatever the runtime treats as a literal) or logged as `fail to parseInt: <expression>`. Dynamic attributes need a `<Transform target="x" value="...">` (or `target="alpha"`) *child element* instead - the same `target`/`value` pattern `Variant` already uses for ambient-mode.
  - This also silently broke the hour-tens digit's visibility condition (task 2.3): it happened to render correctly throughout testing purely because testing stayed within the 10/11/12 o'clock window, not because the condition actually worked - logcat showed `fail to parseInt` for that `alpha` expression too. Fixed the same way, via `<Transform target="alpha" value="...">`.
  - With `Transform` used correctly, the sprite now genuinely drifts back and forth across the river per `[SECOND]` (confirmed at two different second values, clearly different x positions).
  - River and jet art also redone after user feedback that the first pass looked nothing like a retro game: river now has grassy top/bottom banks and a sine-wave water pattern; jet is a clearer top-down silhouette (nose, fuselage, swept wings, twin tail fins) defined via explicit filled-column ranges per row instead of hand-typed ASCII art.
